## 3. Information Leakage Audit

### 3.1 OpenAPI Documentation (PUBLIC)

**Status**: **EXPOSED**

FastAPI auto-generates three public endpoints:
- `GET /docs` — Swagger UI (interactive API explorer)
- `GET /redoc` — ReDoc documentation
- `GET /openapi.json` — Raw OpenAPI spec

These expose:
- Every endpoint path, method, and parameter
- Request/response schemas (including internal models like `ExchangeResponse`, `RefreshTokenRequest`)
- Query parameter names and types
- Auth scheme definitions (HTTPBearer)

**Source**: `main.py:195` — `FastAPI()` constructor has no `docs_url=None` or `redoc_url=None`.

### 3.2 Error Response Detail

**Status**: Mostly good, some leakage

| Error | Detail | Risk |
|---|---|---|
| JWT verification failure | `detail=str(exc)` in `middleware.py:29` | **Medium** — could expose PyJWT internals (key ID, algorithm info) |
| Issuer rejection | `"Issuer not allowed: {iss}"` | Low — confirms which issuers are rejected |
| Audience rejection | `"Audience not allowed: {aud}"` | Low — confirms which audiences are rejected |
| Domain rejection | `"Domain not allowed: {domain}"` | Low — confirms domain from the token |
| Admin writes disabled | `"RBAC write operations not configured (admin SA key not set)"` | **Medium** — reveals infrastructure setup detail |
| `redirect_uri` rejection | `"Invalid redirect_uri: not in allowlist"` | Low |

### 3.3 Response Headers

**Status**: Default Uvicorn/Starlette headers

- `server: uvicorn` is included by default in Uvicorn responses
- No `X-Powered-By` header (Starlette does not add one)
- No explicit `X-Content-Type-Options`, `X-Frame-Options`, or `Strict-Transport-Security` headers

### 3.4 Session Cookie Security

**Status**: **Good**

From `login.py:135-143`:
```python
response.set_cookie(
    key="session_id",
    value=signed_session_id,
    httponly=True,     # ✅ Not accessible via JavaScript
    secure=True,       # ✅ HTTPS only
    samesite="lax",    # ✅ Mitigates CSRF for cross-origin POST
    path="/",
    max_age=settings.session_ttl,
)
```

Cookie value is signed with `itsdangerous.URLSafeSerializer` using `session_secret_key`. Server-side session data is stored in `InMemorySessionStore` — nothing sensitive in the cookie itself.

### 3.5 OAuth CSRF State

**Status**: **Adequate**

- State is a UUID4, stored in module-level `_pending_states` dict (`login.py:28`)
- State is validated and consumed (popped) on callback (`login.py:93-95`)
- **Issue**: No TTL on pending states — abandoned OAuth flows leak memory indefinitely

### 3.6 Token Exposure in URLs

**Status**: **CLI flow uses query parameter**

- `_handle_cli_callback` redirects to `localhost?token=<JWT>` (`login.py:180`)
- Standard pattern for localhost OAuth callbacks, but token is visible in browser history
- Auth codes for external redirects also passed via query param (`login.py:163`) — standard OAuth behavior, mitigated by single-use + 5min TTL

### 3.7 CORS Configuration

**Status**: **Conditional — safe when unconfigured**

From `main.py:202-209`:
- Only added when `ALLOWED_ORIGINS` env var is set
- `allow_credentials=True` — necessary for cookie-based auth cross-origin
- `allow_methods=["GET", "POST"]` — appropriately restrictive
- No wildcard origin support when credentials are enabled (Starlette enforces this)

### 3.8 Starlette SessionMiddleware

**Status**: **Present but potentially confusing**

- `SessionMiddleware` (`main.py:211`) is added for Authlib OAuth state management
- Uses a separate `session_secret_key` — this creates a Starlette-signed `session` cookie
- The application's own session system uses a different `session_id` cookie with `itsdangerous`
- Two session cookies exist simultaneously — the Starlette one is used only by Authlib internally

## 4. Auth Boundary Analysis

### 4.1 JWT-Protected Endpoints (`get_current_user`)

| Scenario | Behavior | Correct? |
|---|---|---|
| No `Authorization` header | 401 Not authenticated | ✅ |
| Malformed Bearer token | 401 (PyJWT decode error) | ✅ |
| Expired JWT | 401 (expired) | ✅ |
| Wrong audience | Token still accepted — **no audience validation in `get_current_user`** | ⚠️ See S-007 |
| Valid JWT | Returns decoded claims | ✅ |
| Realm not configured | 503 Auth service not configured | ✅ |

### 4.2 Exchange Endpoint (`/auth/exchange`)

| Scenario | Behavior | Correct? |
|---|---|---|
| No Bearer | 401 | ✅ |
| Valid JWT, unauthorized issuer | 403 | ✅ |
| Valid JWT, unauthorized audience | 403 | ✅ |
| Valid JWT, unauthorized domain | 403 | ✅ |
| Google access token, valid | Validates via tokeninfo → signs Type C JWT | ✅ |
| Access token, unauthorized audience | 401 (via `validate_access_token`) | ✅ |
| Caller-controlled expiry (query param) | `expiry` defaults to 3600, **no upper bound** | ⚠️ See S-006 |

### 4.3 Token Endpoint (`/auth/token`)

| Scenario | Behavior | Correct? |
|---|---|---|
| No session, no Bearer | 401 | ✅ |
| Valid session cookie | Extracts email, signs Type C JWT | ✅ |
| Valid Bearer JWT | Extracts email, signs Type C JWT | ✅ |
| No `service` param | 400 | ✅ |
| Token issuer not configured | 503 | ✅ |

### 4.4 Session-Protected Endpoints

| Scenario | Behavior | Correct? |
|---|---|---|
| No cookie | 307 redirect to `/ui/login` | ✅ |
| Tampered cookie | 307 redirect (BadSignature caught) | ✅ |
| Expired session (deleted from store) | 307 redirect | ✅ |
| Valid session, not admin | 403 (for admin UI pages) | ✅ |

### 4.5 Admin Endpoints

| Scenario | Behavior | Correct? |
|---|---|---|
| Valid JWT, has admin RBAC role | Access granted | ✅ |
| Valid JWT, in admin email whitelist | Access granted (fallback) | ✅ |
| Valid JWT, not admin | 403 | ✅ |
| Write operation, no admin SA | 503 "admin SA key not set" | ⚠️ See S-003 |

### 4.6 Auth Code Flow

| Scenario | Behavior | Correct? |
|---|---|---|
| Single-use code | Code consumed (popped) on first use | ✅ |
| Expired code (>5min) | Pruned and rejected | ✅ |
| Replay attempt | Returns None (already consumed) | ✅ |
| Wrong redirect_uri | Returns None (mismatch check) | ✅ |

### 4.7 Refresh Endpoint (`/auth/refresh`)

| Scenario | Behavior | Correct? |
|---|---|---|
| No auth required to call | **Yes — validates via Google** | ⚠️ See S-008 |
| Invalid refresh token | 401 (Google rejects) | ✅ |
| Valid refresh token | Signs dockmaster JWT | ✅ |
| Returns Google tokens in response | `id_token` + `access_token` included | ⚠️ See S-009 |
| Uses `signer.get_token()` (Type B, SA-signed) | Inconsistent with Type C elsewhere | ⚠️ See S-010 |

### 4.8 Semi-Public Endpoints (`/auth/principal`, `/auth/sessions`)

| Scenario | Behavior | Correct? |
|---|---|---|
| No cookie | Returns `{}` | ✅ |
| Valid cookie | Returns session data / user's sessions | ✅ |
| No 401 — always succeeds | By design (UI convenience) | ✅ |

## 5. Gap Analysis

| ID | What | Risk | Category | Recommendation |
|---|---|---|---|---|
| S-001 | **OpenAPI docs publicly accessible** — `/docs`, `/redoc`, `/openapi.json` expose full API surface, schemas, and parameter names to unauthenticated users | **High** | Info Leakage | Set `docs_url=None, redoc_url=None, openapi_url=None` in `FastAPI()` constructor for production. Optionally keep them behind admin auth or a dev-only flag. |
| S-002 | **JWT decode errors leak internals** — `middleware.py:29` passes `str(exc)` from PyJWT directly to the 401 detail. Could reveal key ID, algorithm, or decode context. | **Medium** | Info Leakage | Replace with generic `"Invalid or expired token"` message. Log the actual error server-side. |
| S-003 | **503 detail leaks infrastructure** — `require_admin_writes` returns `"RBAC write operations not configured (admin SA key not set)"`. Reveals SA key architecture to callers. | **Low** | Info Leakage | Simplify to `"Write operations not available"`. |
| S-004 | **No security response headers** — Missing `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Strict-Transport-Security`. Standard hardening headers for web applications. | **Medium** | Config | Add a middleware or Caddy-level config to set security headers. `X-Frame-Options: DENY` is especially important since the admin UI serves HTML. |
| S-005 | **OAuth state has no TTL** — `_pending_states` dict in `login.py` grows indefinitely for abandoned OAuth flows. No cleanup mechanism. | **Low** | Session Security | Add a TTL or max-size pruning. Could use the same pattern as `AuthCodeStore` (prune on access, 5min TTL). |
| S-006 | **Unbounded token expiry on `/auth/exchange`** — `expiry` query param (`exchange.py:105`) has no upper bound. A valid caller can request tokens lasting days/years. | **Medium** | Token Security | Add a `max_token_ttl` setting and cap the requested expiry. Default cap could be 86400 (24h). |
| S-007 | **`get_current_user` doesn't validate audience** — The JWT middleware (`middleware.py`) verifies signature but does not check that the token's `aud` claim matches dockmaster. Any valid dockmaster-signed JWT (for any target service) is accepted. | **Medium** | Auth Bypass | Add audience validation to `get_current_user` or document that audience-scoped access control is the caller's responsibility. Endpoints like `/auth/has` and `/auth/grants` accept tokens for any audience. |
| S-008 | **`/auth/refresh` requires no dockmaster auth** — Anyone with a valid Google refresh token + correct client_id can mint a dockmaster JWT. Auth is delegated entirely to Google. | **Low** | Token Security | This is by design (re-validates via Google), but should be documented as an intentional decision. The domain check on the returned id_token provides the boundary. |
| S-009 | **`/auth/refresh` returns Google tokens** — `RefreshResponse` includes raw `id_token` and `access_token` from Google. These can be used to call Google APIs directly. | **Medium** | Info Leakage | Consider whether the response should include Google tokens. If the caller needs them, this is intentional. If not, remove them to reduce the blast radius of a compromised response. |
| S-010 | **`/auth/refresh` still uses SA-signed JWT (Type B)** — While exchange and token endpoints issue Type C (ephemeral-signed) JWTs, refresh still uses `signer.get_token()` (Type B, SA-signed). | **Low** | Token Security | Migrate to `token_issuer.sign()` for consistency. Already noted as D29 vocab unification item. |
| S-011 | **CLI token in URL query param** — `_handle_cli_callback` passes JWT as `?token=...` in redirect to localhost. Visible in browser history and potentially server logs. | **Low** | Token Security | Standard for localhost OAuth flows. Fragment-based delivery (`#token=...`) would avoid browser history but complicates the CLI callback server. Acceptable for localhost-only scope. |
| S-012 | **Two session cookie mechanisms** — Starlette `SessionMiddleware` creates a `session` cookie (for Authlib OAuth state). The application creates a separate `session_id` cookie (for user sessions). Two signing keys, two cookie lifecycles. | **Low** | Config | Not a security vulnerability per se, but adds surface area and potential confusion. Document this dual-cookie architecture. |
| S-013 | **403 responses reveal config details** — Domain, issuer, and audience rejection messages include the rejected value (e.g., `"Domain not allowed: evil.com"`). Useful for debugging but reveals authorization policy to attackers. | **Low** | Info Leakage | Consider generic rejection messages for production. Keep detailed messages for structured logging. |
| S-014 | **`GET /` exposes docs URL** — `ServiceInfo` response includes `"docs": "/docs"`, directly pointing unauthenticated users to the API documentation. | **Low** | Info Leakage | Remove the `docs` field from the root response, or make it conditional on the docs endpoint being enabled. |
